### 3) DB 설계 할때 user 테이블에서 id라는 변수명을 쓰고, user_allergies 테이블에서 id라는 변수명을 또 쓴다니 이거 괜찮은거야?!

> 아무리 테이블이 다르다고 해도... 변수명을 똑같이 통일하다니 이거 문제가 생기는거 아니야..?!

- 그에 대답은 `"괜찮다!"`이다!

- 관습적으로 이렇게 많이 진행하며, 이유가 몇가지 있다!

  1. **그 테이블 안에서는 `id`만 봐도 의미가 명확함**

     - `users` 테이블의 `id`는 당연히 사용자 ID고, `meal_histories` 테이블의 `id`는 당연히 먹히스토리 ID이다. 존재하는 테이블이 다르기 때문에 헷갈릴 이유도 없고, 오히려 해당 테이블의 `id` 값이라는 느낌이 명확하다!

  2. **ORM에서 다루기 편하다**

     - Spring Data JPA를 쓸 때 엔티티마다 기본키 필드를 보통 이렇게 둔다.

       ```
       @Id
       private UUID id;
       ```

       **모든 엔티티가 `id`라는 기본키를 가지면 공통 처리, 조회, 상속 구조를 만들기 쉽다.**

  3. **외래키에서만 의미를 붙이면 관계가 선명해진다.**

     - ```
       meal_histories.id
       meal_histories.user_id
       meal_histories.recommendation_id
       meal_histories.recommended_food_id
       ```

       - 여기서 `id`는 “이 기록 자체의 ID”이고, `user_id`는 “연결된 사용자 ID”예요. 구분이 꽤 깔끔해진다.

### 4) 왜 굳이 테이블을 나누는 걸까?

> user_allergies 테이블의 구성을 보면 id, user_id, name으로 3개의 값이 들어있다
>
> 그런데 이러면 굳이 조회만 늘어나는 것 아닌가... 싶다 그냥 user 테이블에 다 때려 넣어도 괜찮을 것 같은데? 왜 그런거지?

- **이는 제 1정규화의 일종이다!**

- **`"제 1정규화"` **= **한 컬럼에는 하나의 원자값만 들어가야 한다는 규칙.**
  - 현재 user_allergies의 값은 개인당 n개의 값이 들어갈 수 있다. 즉, 하나의 원자값만 들어가야 한다는 규칙이 불가능하다는 뜻!
- 즉 테이블을 나누어 각각 1개의 원자값으로 나누어 저장하는 행위가 **제 1정규화에 해당 되어서 그런 것!**



### 5) refresh_token의 DB에서 `revoked=true`는 무엇일까?

- **`revoked=true`**의 값은 사용자가 로그아웃을 한다면 요청을 보고 이 값을 true로 바꾸는 것이다.
- `revoked=true` 상태에서는 요청이 들어와도 요청을 받아들이지 않는다. 즉, `refresh_token`이 탈취 되었더라도, `revoked=true` 상태라면 요청이 거부된다는 것!



### 6) MVP에서는 batch 없이 수동 seed 데이터로 시작해도 된다. ...? 이게 뭔소리야?

> 이달의 인기 음식 기능에서 **"MVP에서는 batch 없이 수동 seed 데이터로 시작해도 된다."** 라는 얘기를 들었는데 이게 무슨 소리인걸까...?

- **`batch`는 정해진 시간에 자동으로 돌아가는 작업이다!** 내가 batch를 설정해두면, 정해진 시간에 알아서 값을 분석해서 인기 음식을 자동으로 갱신해주는 것이다!

- 이거 진짜 좋다..!

- **수동 seed 데이터는 개발자가 미리 넣어두는 초기 데이터를 말한다!**
  - 그냥 임의로 넣어두어도 된다는것이다! 시간이 남으면 batch까지 진행해보는 방식이 좋겠다!
